# Laranet Ecosystem Architecture

## 1. Purpose

This document describes the long-term architecture of the Laranet ecosystem: its
identity, package boundaries, dependency rules, planned modules, and the path from
`0.1.0` to `1.0.0`.

It is a planning document. A module listed here is not implemented unless its status
says so. The roadmap in [`docs/roadmap/`](../roadmap/README.md) defines when work is
scheduled.

## 2. Identity

Laranet is a **modular toolkit with framework-like tooling** for .NET.

It provides conventions, project templates, code generation, and optional
integrations on top of native .NET. It does not provide its own application host,
runtime lifecycle, ORM, dependency injection container, validation engine, or view
engine.

See [ADR-0006](decisions/0006-toolkit-with-framework-tooling.md).

The guiding principle remains:

> Don't make .NET look like Laravel. Make .NET feel better to work with.

## 3. Principles

1. **Native .NET first.** Use ASP.NET Core, EF Core, dependency injection, and
   configuration directly instead of wrapping them without a demonstrated gap.
2. **Modularity.** Every package is independently consumable. No module forces the
   installation of unrelated dependencies.
3. **Convention over configuration.** Sensible defaults reduce boilerplate.
4. **Architectural freedom.** Users choose their structure: minimal API, MVC,
   layered, hexagonal, or modular. Laranet does not impose one.
5. **Escape hatches.** Generated code and abstractions must allow direct use of the
   underlying .NET APIs at any time.
6. **No unnecessary abstractions.** `Result`, `Error`, Repository, Unit of Work, CQRS,
   and mediator patterns are not generated by default and require a concrete use case.
7. **Editable generated code.** The CLI produces ordinary C# with no mandatory runtime
   metadata. See [ADR-0004](decisions/0004-editable-generated-code.md).
8. **Provider neutrality.** `Laranet.Data` does not depend on EF Core, ASP.NET Core, or
   a database provider.

## 5. Dependency Rules

```text
Laranet (Core)
    ▲
    │
Laranet.Data ◄── Laranet.EntityFrameworkCore
    ▲
    │
Laranet.AspNetCore ◄── Laranet.AspNetCore.Validation
    ▲
    │
Laranet.Admin.AspNetCore ◄── Laranet.Admin ◄── Laranet.Data

Laranet.Cli ──► generated projects (no runtime dependency)
```

The rules are:

1. `Laranet` must not depend on any module, framework, or provider. It stays empty
   until an abstraction is required by at least two modules. See
   [ADR-0005](decisions/0005-intentionally-empty-core.md).
2. `Laranet.Data` must not depend on EF Core, ASP.NET Core, or a database provider.
3. `Laranet.EntityFrameworkCore` may depend on `Laranet.Data` and EF Core abstractions.
   It must not depend on a specific database provider package.
4. `Laranet.AspNetCore` may depend on `Laranet.Data` and the ASP.NET Core shared
   framework.
5. `Laranet.Admin` must not depend on EF Core. It depends on data adapter contracts
   implemented by integrations.
6. No runtime module may depend on `Laranet.Cli`.
7. Optional integrations must not become mandatory dependencies of unrelated modules.

### Provider strategy

The official relational providers are:

- SQLite
- PostgreSQL
- MySQL / MariaDB
- SQL Server

They are verified through a CI test matrix, not through separate packages. A
per-provider package is justified only when it exposes provider-specific
functionality. Creating packages solely to group NuGet dependencies adds maintenance
without value.

## 6. Architectural Profiles

Profiles are CLI templates and generation presets. They are not runtime modules.

| Profile | Use case | Default |
| --- | --- | --- |
| `minimal-api` | Small HTTP services and APIs | Yes for APIs |
| `mvc` | Traditional web applications with Razor views | No |
| `layered` | Business applications with presentation, application, domain, and infrastructure projects | No |
| `hexagonal` | Systems with explicit ports and adapters | No |
| `modular` | Feature folders and module boundaries | No |

Every profile must:

- Generate a project that builds without warnings.
- Use native ASP.NET Core, EF Core, and dependency injection.
- Include only the layers the profile promises.
- Be covered by generation and build tests.
- Document its trade-offs.

`make:crud` has its own profiles (`simple`, `standard`, `clean`, `modular`). The
default is `simple`. See [ADR-0007](decisions/0007-simple-generation-profile.md).

## 7. Data Strategy

| Technology | Role | Commitment |
| --- | --- | --- |
| EF Core | Primary ORM and query provider | Official |
| Dapper | Micro-ORM for explicit SQL | Candidate adapter |
| ADO.NET | Direct, controlled access | Candidate adapter |
| Laranet ORM | Own ORM | Research only |

Laranet must simplify EF Core without hiding it. Users must be able to use
`DbContext`, `IQueryable`, `Include`, Fluent API, migrations, and native EF Core APIs
at any time.

A Laranet ORM would need to solve materialization, mapping, relationships, change
tracking, expressions, transactions, migrations, concurrency, providers,
asynchrony, and cancellation. It is not a committed deliverable and will not start
without a technical justification and an ADR.

## 8. Admin Module (Django-inspired)

An administrative panel that builds list, search, filter, create, edit, and delete
screens from resource metadata is a valuable differentiator. It is a **candidate for
[Version 4](../roadmap/v4.md)**, not part of V3.

Proposed boundaries:

- `Laranet.Admin` contains resource metadata, list/filter/search/page contracts,
  form metadata, and permission hooks.
- `Laranet.Admin.AspNetCore` renders the panel with Razor and integrates with
  ASP.NET Core authentication and authorization.
- Data access is provided through an adapter contract, so EF Core, Dapper, or ADO.NET
  can implement it.
- The panel is optional and never a dependency of other modules.
- No custom view engine, authentication system, or authorization model is introduced.

Before implementation, the project needs:

1. An ADR defining the adapter contract and security model.
2. A prototype validated against a real application.
3. Tests covering authentication, authorization, filtering, pagination, and CRUD.
4. A clear story for users who do not use EF Core.

## 9. Module Admission Gates

A new module enters the ecosystem only when it satisfies all of these:

- A documented, concrete use case exists.
- It has a distinct responsibility that does not fit an existing module.
- Its dependency direction respects section 5.
- It can be distributed and consumed independently.
- It has unit tests and integration tests where behavior depends on a provider or
  framework.
- Its public API is documented with XML documentation.
- Its maintenance cost is understood and accepted.
- An ADR records the decision when it affects architecture or public contracts.

| `1.0.0` | Stabilization | API freeze, compatibility guarantees, documentation | Future |

The exact version assigned to each milestone will be confirmed when the milestone
starts. Versions remain synchronized across all packages in a release.

## 11. Explicit Non-goals

- A transversal `Result<T>` / `Error` pattern.
- Repository, Unit of Work, or CQRS generated by default.
- Replacing ASP.NET Core, EF Core, dependency injection, configuration, or logging.
- A custom view engine, validation engine, or authentication system.
- Per-provider packages without provider-specific functionality.
- A custom ORM committed before a technical justification exists.
- New modules without a documented use case.
