# Version 5 — `1.0.0`: the stability contract

**Status: Planned (gated by Version 4)**
**Target release: `1.0.0`**

Version 5 is the first stable release of Laranet. It is not the version with every
feature; it is the version where the published surface becomes a compatibility
commitment.

`1.0.0` means: **existing applications will not break because Laranet changes.** It
does not mean that every capability in the roadmap is already implemented. New
packages and APIs can be added in `1.x` releases without a major version.

This milestone follows [ADR-0008](../architecture/decisions/0008-runtime-and-tooling-versioning.md),
which defines `1.0.0` as a statement about the runtime surface and allows tooling to
follow its own cadence when a documented trigger is met.

## 1. Prerequisites

Version 5 does not start until all of the following are true:

- [ ] [Version 4](v4.md) exit criteria are met, or the admin milestone is explicitly
      postponed and removed from the `1.0` surface.
- [ ] At least one real application runs on the Version 3 templates and, when
      available, the Version 4 admin.
- [ ] The provider matrix is green for SQLite, PostgreSQL, MySQL/MariaDB, and SQL
      Server.
- [ ] The feedback backlog has been reviewed and the `1.0` scope has been frozen.
- [ ] The diagnostics catalog ADR is accepted if analyzers are included. See the
      [ADR index](../architecture/decisions/README.md).

If a prerequisite fails, `1.0.0` is postponed. It is not released with a smaller
compatibility promise or with undocumented gaps.

## 2. What `1.0.0` commits to

- **Public API stability.** No breaking change without a major version.
- **Documented behavior.** Every public API has XML documentation, examples, and
  documented edge cases.
- **Provider expectations.** Behavior that depends on the database is documented as
  provider-dependent instead of promised uniformly.
- **Deprecation before removal.** APIs are marked obsolete with an alternative before
  they are removed.
- **Migration guidance.** Every breaking change has a migration path.
- **Supported versions.** The support window is explicit and tied to the compatibility
  policy.
- **Verifiable artifacts.** Packages are validated in CI and, where the ecosystem
  supports it, signed and accompanied by a dependency inventory.

## 3. Scope

The scope is the smallest surface that can be defended as `1.0`. It has five
workstreams.

### 3.1 Release integrity

This workstream is not optional. It is the difference between a version number and a
promise.

- [ ] Run a public API compatibility gate in CI
      (`Microsoft.DotNet.ApiCompat` or `PublicApiAnalyzers`) and fail on unapproved
      changes.
- [ ] Extend `verify-packages.sh` to validate the release train, dependencies, and
      metadata for every package in the `1.0` surface.
- [ ] Generate an SBOM for each release.
- [ ] Run an automated dependency vulnerability scan.
- [ ] Evaluate package signing and artifact attestations; adopt them if the
      operational cost is acceptable and the ecosystem supports verification.
- [ ] Document the release checklist, rollback procedure, and CVE response policy.
- [ ] Publish a concrete support window in the support policy.

### 3.2 Data Experience

This is where Laranet has the clearest identity and the lowest risk of becoming a
framework wrapper.

- [ ] **Dynamic filtering.** Implement an allowlisted, expression-based filter API
      with a small operator set:
      `Equals`, `NotEquals`, `Contains`, `StartsWith`, `GreaterThan`,
      `GreaterThanOrEqual`, `LessThan`, `LessThanOrEqual`, `In`, `Between`, `IsNull`.
  - The typed API is the primary contract; the dynamic facade is opt-in for query
    strings.
  - Filters compose into one expression tree and preserve provider translation.
  - No expression parser, no free-form DSL, no in-memory fallback.
  - Property paths are top-level in the first version; nested paths are evaluated
    separately.
- [ ] **Keyset pagination.** Research the provider translation first.
  - Implement only if SQLite, PostgreSQL, and SQL Server translate the same
    expression tree.
  - Provide a `CursorPage<T>` with an opaque cursor and no mandatory total count.
  - Document the ordering requirements and the limitations for nullable keys.
  - If translation does not hold, record the decision and defer.
- [ ] **EF Core conventions at production quality.** Carry the Version 3 conventions
      through the provider matrix:
  - `CreatedAt` / `UpdatedAt` / `CreatedBy` / `UpdatedBy` via an opt-in interceptor.
  - Soft delete via a marker interface and a global query filter.
  - Optimistic concurrency via a concurrency token.
  - Full change history is **not** part of `1.0`; it is a separate feature with
    retention and privacy implications.
- [ ] Document the native bulk operations (`ExecuteUpdateAsync`,
      `ExecuteDeleteAsync`) instead of wrapping them.
- [ ] Verify that global query filters, projections, and pagination compose correctly.

### 3.3 Diagnostics

Diagnostics are valuable only if they are small, specific, and stable.

- [ ] Implement `Laranet.Analyzers` with a maximum of **8–10 rules**, limited to real
      Laranet misuse:
  - Pagination without deterministic ordering.
  - Dynamic sorting without an allowlist.
  - Dynamic filtering without an allowlist.
  - Synchronous pagination in an asynchronous endpoint.
  - EF Core entities exposed as API responses.
  - Incompatible Laranet package versions.
  - Missing `CancellationToken` in asynchronous EF Core calls.
- [ ] Treat diagnostic IDs as permanent public identifiers. Severity may change; the
      ID may not be recycled.
- [ ] Share only the diagnostic descriptors with `laranet doctor`; do not share the
      Roslyn engine. The doctor must not depend on Roslyn.
- [ ] Do not duplicate generic rules already covered by .NET analyzers, StyleCop,
      Roslynator, or architecture tests.

If the rule set cannot meet the `1.0` stability bar, the analyzer is omitted from
Version 5 rather than forcing an unplanned version split.

### 3.4 Developer Experience

The ecosystem is demonstrated by a working application, not by a package diagram.

- [ ] Add an `enterprise-api` template that wires, using native .NET:
  - Minimal API or MVC.
  - EF Core with migrations.
  - Authentication and authorization through ASP.NET Core Identity or JWT.
  - OpenAPI.
  - `ProblemDetails` and a consistent error contract.
  - Validation.
  - Search, filtering, sorting, and pagination.
  - Health checks, logging, and OpenTelemetry.
  - Rate limiting, CORS, and configuration by environment.
  - Dockerfile and CI workflow.
  - A small integration test suite.
- [ ] Add a reference application in `samples/` that uses the template and a real
      domain with at least two related entities.
- [ ] Add database-first scaffolding to the CLI, wrapping
      `dotnet ef dbcontext scaffold` with Laranet conventions.
- [ ] Add opt-in integration test generation (`make:crud --with-tests`).
- [ ] Add CLI commands only for features that already exist.
- [ ] Ensure every generated project builds without warnings in CI.

### 3.5 Documentation and migration

- [ ] Publish a migration guide from the latest `0.x` release to `1.0.0`.
- [ ] Complete the API reference for the frozen surface.
- [ ] Document provider-dependent behavior and known limitations.
- [ ] Publish a third-party extension guide: how to ship a package that extends
      Laranet without coupling to internal types.
- [ ] Document the deprecation workflow with a worked example.
- [ ] Document that Native AOT and trimming support is limited by EF Core and must be
      evaluated per application; it is not a `1.0` guarantee.

## 4. Non-goals

The following capabilities are deliberately excluded from `1.0`:

- Modular application framework (`Laranet.Modules`, `Laranet.Application`).
- Domain events, outbox, and messaging.
- Background jobs and schedulers.
- Multi-tenancy.
- A full audit-history engine.
- A resource-serialization engine (API Resources beyond generated code and thin
  helpers).
- A meta-package that installs the whole ecosystem.
- `Result<T>` / `Error`, CQRS, mediator, Repository, or Unit of Work.
- An ORM, HTTP server, view engine, authentication system, caching layer, mail system,
  storage abstraction, or background job runner.
- Native AOT/trimming as a release gate.
- Per-provider packages without provider-specific functionality.

`Laranet` remains intentionally empty during the `1.0` release unless a shared
abstraction is required by at least two modules. See
[ADR-0005](../architecture/decisions/0005-intentionally-empty-core.md).

## 5. Phases

The phases are ordered by dependency, not by sprint number.

| Phase | Deliverable | Exit condition |
| --- | --- | --- |
| 1 | Freeze and release integrity | The surface is frozen and the compatibility gate is enforced. |
| 2 | Data Experience | Filtering, keyset decision, and conventions are tested across providers. |
| 3 | Diagnostics | The analyzer catalog is stable, documented, and optional. |
| 4 | Developer Experience | The enterprise template and reference application build and run. |
| 5 | Documentation and migration | The migration guide and API reference are complete. |
| 6 | Release candidate | A real application upgrades across a minor with documented changes only. |

Phase 6 is a validation gate, not a new feature phase. If validation exposes a design
problem, the fix belongs in the earlier phase that caused it.

## 6. Exit criteria

`1.0.0` is released only when all of the following are true:

- [ ] The public API of every `1.0` package is frozen and documented.
- [ ] The API compatibility gate is green and blocks unapproved changes.
- [ ] The provider matrix is green for SQLite, PostgreSQL, MySQL/MariaDB, and SQL
      Server.
- [ ] At least one real application has upgraded across a minor release using only
      documented changes.
- [ ] The `enterprise-api` template and the reference application build in CI.
- [ ] Filtering is implemented with provider tests, or explicitly deferred with an
      accepted decision.
- [ ] Keyset pagination is implemented with provider tests, or explicitly deferred
      with an accepted decision.
- [ ] The analyzer catalog contains no more than 10 rules and every ID is documented.
- [ ] Supply-chain checks run for the release: SBOM, vulnerability scan, and artifact
      verification where supported.
- [ ] No release-blocking defect is open.
- [ ] The migration guide is published before the release announcement.

## 7. Decision log

| Decision | Outcome |
| --- | --- |
| Version 5 identity | First stable release, `1.0.0` |
| Meaning of `1.0.0` | Compatibility promise, not feature completeness |
| `1.0` surface | Only published and stable packages; admin is included only if Version 4 delivered it |
| Modules, events, jobs, tenancy | Deferred to [Version 6](v6.md) |
| Core package | Stays empty unless two modules need a shared abstraction |
| Meta-package | Not planned; the template is the entry point |
| API Resources | Generated code and thin helpers, not a serialization engine |
| Diagnostics | Optional, small catalog, permanent IDs |
| AOT/trimming | Documented limitation, not a release gate |

## 8. Backlog epics

| Epic | Includes |
| --- | --- |
| Release Integrity | API compatibility, SBOM, signing, vulnerability scanning, release checklist |
| Data Experience | Dynamic filtering, keyset pagination, EF Core conventions |
| Diagnostics | Analyzer catalog, doctor integration, diagnostic documentation |
| Developer Experience | Enterprise template, reference application, database-first scaffolding, test generation |
| Documentation | Migration guide, API reference, support policy, extension guide |

Create one issue per significant deliverable. Do not create one issue per checklist
item, and do not duplicate the roadmap content in issues.
