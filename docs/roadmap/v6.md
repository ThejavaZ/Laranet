# Version 6 — Application capabilities after `1.0`

**Status: Direction (not scheduled)**
**Target: `1.x` minor releases**

Version 6 is the parking lot for application capabilities that are valuable but do
not belong in the `1.0` stability contract. Nothing here is committed until a real
application needs it and the corresponding ADR is accepted.

The guiding rule is simple: **`1.0` freezes a small surface; `1.x` grows it without
breaking who already depends on it.**

## 1. Prerequisites

A candidate enters Version 6 only when:

- [ ] `1.0.0` is published and the compatibility gate is running.
- [ ] At least two real applications need the capability, or one application needs it
      in a way that cannot be solved with native .NET or a focused third-party
      library.
- [ ] An ADR defines the public contract, the dependency direction, and the
      compatibility impact.
- [ ] The change is additive and can ship in a minor version.
- [ ] The capability passes the
      [module admission gates](../architecture/ecosystem.md#9-module-admission-gates).

If a candidate would require a breaking change, it waits for the next major version
instead of being forced into `1.x`.

## 2. Candidates

### 2.1 Modular monolith support

A minimal composition model for applications organized by feature or business module.

- Explicit registration, for example
  `builder.Services.AddLaranetModules(typeof(UsersModule), typeof(OrdersModule))`.
- `IModule` with `Register(IServiceCollection)` and `Map(IEndpointRouteBuilder)`.
- No dynamic plugin loading, no assembly scanning by default, no per-module runtime
  isolation.
- Migrations remain application-wide. Per-module migrations are not part of the first
  version.
- A module is a composition boundary, not a deployment boundary.

**Decision gate:** an ADR and at least one application organized as a modular
monolith.

### 2.2 API Resources

Consistent transformation from entities or projections to HTTP responses.

- Generated `ProductResource.From(product)` code as the default.
- Optional thin helpers for page metadata and links.
- No attribute-driven serialization engine, no HATEOAS framework, no replacement for
  `System.Text.Json`.
- Projection remains the recommended path for read endpoints.

**Decision gate:** the reference application shows the same response conventions in at
least three endpoints, and the helper removes real duplication.

### 2.3 Full audit history

Beyond timestamps and user stamps:

- Previous and new values.
- Operation type and responsible user.
- Search by entity.
- Retention and privacy policy.

This is not part of `1.0` because it requires storage design, retention rules, and a
privacy story. Before implementing it, evaluate database-native options such as
temporal tables and proven audit libraries.

**Decision gate:** a documented compliance or business requirement that timestamps and
user stamps do not satisfy.

### 2.4 Domain events

In-process notifications are easy to write and easy to misuse. Reliable delivery
requires an outbox, idempotency, and retry semantics.

- Start with an in-process dispatcher only if the contract is explicit about its
  guarantees.
- Do not call it reliable messaging.
- For cross-process delivery, integrate a proven library or broker.
- Do not introduce `IRequest<T>` / `IHandler<,>` contracts in the core package.

**Decision gate:** at least one application has a side effect that must happen after a
committed transaction and cannot be handled inline.

### 2.5 Background jobs

One optional adapter at a time, not a scheduler.

- Prefer a proven library such as Hangfire or Quartz.NET.
- The adapter registers jobs and configuration; it does not reimplement scheduling,
  retries, or storage.
- Each adapter is an independent optional package with its own compatibility matrix.

**Decision gate:** a real repeated or long-running task that cannot run inside the
request pipeline.

### 2.6 Permissions

ASP.NET Core policies and `RequireAuthorization` already provide the authorization
model. A Laranet helper would only reduce repetition:

- Optional permission-name conventions.
- Optional endpoint metadata attribute.
- No authentication engine, no role model, no replacement for Identity.

**Decision gate:** the reference application repeats the same policy wiring in several
resources.

### 2.7 CLI extensions

Commands are added only after the runtime capability exists:

- `make:module` after modules exist.
- `make:resource` after resources exist.
- `make:job` after the job adapter exists.
- `make:event` / `make:listener` after events exist.
- `make:policy` only if it generates something more than a policy registration.

Generating empty scaffolds for planned features is explicitly avoided.

### 2.8 Admin evolution

The admin panel is a Version 4 deliverable. Any evolution after `1.0` follows the same
rules: optional package, adapter contract, Razor and ASP.NET Core, no custom view
engine or authentication system.

### 2.9 Authentication and security baseline

Laranet should make a secure starting point available in generated applications
without turning authentication into a mandatory runtime dependency. The Laravel
analogy is useful for the developer experience, not for the implementation: ASP.NET
Core already provides the primitives.

- Prefer an `auth-api` template or an opt-in `--with-auth` option over a package that
  every application must install.
- Use ASP.NET Core Identity for users, password hashing, lockout, and token storage.
- Use `Microsoft.AspNetCore.Authentication.JwtBearer` for JWT access tokens.
- Keep BCrypt optional. BCrypt is a password hashing algorithm, not encryption. If an
  application requires it, integrate it through `IPasswordHasher<TUser>` instead of a
  custom user store.
- No custom authentication engine, user database, JWT implementation, or identity
  model in Core.
- Do not make users, roles, or tokens mandatory in applications that do not need them.
- Cover refresh tokens, revocation, password reset, email confirmation, and secrets
  handling in the template documentation.

**Decision gate:** at least one real application needs the template, an ADR defines
the supported surface, and the implementation remains an optional scaffold over
ASP.NET Core Identity and JWT bearer authentication.

## 3. Explicitly deferred beyond Version 6

### Multi-tenancy

Multi-tenancy is a security boundary, not a feature flag. A first version could use a
shared database and a `TenantId`, but it still requires:

- An ADR and threat model.
- Tenant resolution and execution context.
- Query isolation as defense in depth, not as the only control.
- Tests that prove one tenant cannot read another tenant's data.
- A migration and backup story.

It is not a `1.x` minor feature. It waits for a dedicated milestone and, if it changes
existing contracts, a major version.

### Core package contracts

`Laranet` stays empty until at least two modules need the same abstraction and cannot
depend on each other. The following are **not** candidates:

- `Result<T>` / `Error`.
- `IRequest<T>` / `IHandler<,>` (CQRS/mediator).
- `IClock` (use `TimeProvider`).
- Moving `PagedResult<T>` out of `Laranet.Data`.

If a contract eventually enters Core, it will be a narrowly shared type such as a
tenancy context or an admin resource descriptor, not a general-purpose abstraction.

### Meta-package

A package that installs the whole ecosystem hides the dependency graph and couples
every package to one version. The entry point is a project template, not a
meta-package.

## 4. Exit criteria for Version 6

Version 6 has no single release date. Each candidate is evaluated independently:

- [ ] The candidate is implemented behind an accepted ADR, or rejected with the
      reasoning recorded.
- [ ] The change ships in a minor version without breaking existing applications.
- [ ] The reference application demonstrates the capability.
- [ ] Documentation, tests, and provider coverage match the `1.0` standard.
- [ ] The package graph remains clean and every package is independently consumable.
- [ ] Tooling and runtime versioning follow
      [ADR-0008](../architecture/decisions/0008-runtime-and-tooling-versioning.md).
