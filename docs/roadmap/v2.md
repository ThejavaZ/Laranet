# Version 2 — Adoption, depth, and stabilization

**Status: In progress**
**Priority: Medium**

Version 2 begins after the first public `0.1.0` release. Its primary axis is
**adoption and stability**: close the feedback loop, verify the published packages
against more providers, and only then add functionality that real usage justifies.

The guiding rule is unchanged: a feature enters Version 2 only when a concrete use
case is documented. The items below are candidates, not commitments.

## Principles for Version 2

- Native .NET first: use existing platform capabilities instead of replacing them.
- Keep `Laranet.Data` provider-neutral and independent of EF Core and ASP.NET Core.
- Keep integrations optional and independently consumable.
- Generated code remains ordinary, editable C# with no mandatory runtime metadata.
- No speculative abstractions, including `Result`, `Error`, Repository, or Unit of Work.
- Public API changes require an ADR or a documented compatibility decision.

## Non-goals

- A transversal `Result<T>` / `Error` pattern.
- Repository, Unit of Work, or CQRS abstractions.
- A second web framework, dependency injection container, or validation framework.
- New modules without a demonstrated use case.
- Filling the `Laranet` core package with speculative types.

## Sprint 10 — Provider confidence

**Status: Completed**
**Priority: High**

- [x] Add SQL Server integration tests in CI using a service container.
- [x] Add PostgreSQL integration tests in CI using a service container.
- [x] Cover single and multi-column `Search`, sorting, `WhereIf`, and pagination.
- [x] Promote a provider to "Verified" only when its tests run in CI.
- [x] Document provider-specific translation differences found by the tests.

**Validation:** 234 tests pass on SQLite; the provider compatibility suite passes 9/9
on SQL Server 2022 and 9/9 on PostgreSQL 17. The same suite passes in CI with service
containers.

**Exit criteria:** the compatibility matrix reflects only what the test suite actually
executes.

## Sprint 11 — Query depth (feedback-gated)

**Status: Planned**
**Priority: Medium**

Do not start these items until a concrete use case is documented in an issue.

- [ ] Evaluate keyset (cursor) pagination for large offsets.
  - Requires an ADR covering cursor semantics, ordering requirements, and provider
    translation.
- [ ] Evaluate an optional Roslyn analyzer that warns when `Paginate` or
  `PaginateAsync` is called on a query without a deterministic order.
  - The analyzer must not change runtime behavior and must be independently
    installable.
- [ ] Evaluate additional `Search` scenarios only if users request them.

**Exit criteria:** each implemented item has a documented use case, an ADR when it
changes the public model, and tests.

## Sprint 12 — Ergonomics (feedback-gated)

**Status: Planned**
**Priority: Low**

- [ ] Extensible CLI conventions: configurable folders and namespaces on top of the
  existing `.laranet/templates` mechanism.
- [ ] Additional generators only when a recurring need is demonstrated.
- [ ] Evaluate ASP.NET Core pagination request binding only if real applications
  repeat the same request shape.
- [ ] Keep native model binding, validation, and ProblemDetails unless a gap is
  proven.

## Sprint 13 — Core decision and 1.0 readiness

**Status: Planned**
**Priority: Medium**

- [ ] Keep `Laranet` empty until an abstraction is required by at least two modules.

- [ ] Review XML documentation, samples, and guides against the frozen API.

## Decision log

| Decision | Outcome |
| --- | --- |
| Primary axis | Adoption and stability |
| Core package | Keep empty; document with ADR-0005 |
| Result / Error pattern | Rejected for Version 2 |
| Provider verification | SQL Server and PostgreSQL, promoted only when verified in CI |
| Keyset pagination | Candidate; requires a concrete use case and an ADR |
| Ordering analyzer | Candidate; optional and non-breaking |
| Additional generators | Candidate; only with demonstrated demand |

## Feedback intake

- Use the [Question issue template](https://github.com/TheJavaZ/Laranet/issues/new?template=question.yml)
  for usage questions, ideas, and early proposals. GitHub Discussions may be enabled
  later; the issue templates remain the supported channel.
- Use the bug, documentation, and feature request templates for reproducible defects,
  documentation gaps, and concrete proposals.
- Record recurring requests and validate them against real applications before
  adding them to this roadmap.
- Document the decision and its use case before implementation.

Additions must be justified by concrete use cases, not speculation. Version 2 must
preserve the Version 1 principles: native .NET behavior, provider neutrality,
optional integrations, editable generated code, and no mandatory runtime metadata.
