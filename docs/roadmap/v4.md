# Version 4 — Application surface and admin experience

**Status: Planning (candidate)**
**Priority: Low until Version 3 is complete**

Version 4 explores the first real **application surface** for Laranet: an optional
administrative panel, web and Blazor project templates, and a small set of optional
data adapters. It does not replace ASP.NET Core, EF Core, Razor, Blazor, or Identity;
it packages conventions and tooling on top of them.

This milestone is a candidate, not a commitment. It does not start until the
[Version 3](v3.md) exit criteria are met and the administrative panel has passed its
own admission gates.

## 1. Where Version 4 fits

| Version | Theme | Main outcome |
| --- | --- | --- |
| Version 1 | Foundation | Data, EF Core, ASP.NET Core, and CLI published as `0.1.0`. |
| [Version 2](v2.md) | Adoption and stability | `0.1.1`, real feedback, verified providers. |
| [Version 3](v3.md) | Application experience | Standards, templates, `make:crud`, EF conventions, validation, `laranet doctor`. |
| Version 4 | Application surface | Admin panel, web/Blazor templates, optional adapters. |
| `1.0.0` | Stabilization | Frozen public API and compatibility guarantees. |

Version 4 is the "another `0.x` iteration" that
[Version 3, Sprint 21](v3.md#sprint-21--10-readiness) may choose before `1.0.0`. The
exact version assigned to each sprint is confirmed when the milestone starts.

## 2. Prerequisites

Version 4 does not begin until all of the following are true:

- [ ] Version 3 is published and its exit criteria are met.
- [ ] At least one real application has validated the Version 3 templates and
      `make:crud`.
- [ ] The admin ADR is accepted (Sprint 22).
- [ ] A working prototype has been validated against a real application.
- [ ] The admin security model has been reviewed.
- [ ] The provider matrix is green for SQLite, PostgreSQL, MySQL/MariaDB, and SQL
      Server.
- [ ] The feedback backlog has been reviewed and prioritized.

If any prerequisite fails, the milestone is reduced or postponed rather than partially
implemented.

## 3. Principles

- [ADR-0006](../architecture/decisions/0006-toolkit-with-framework-tooling.md):
  Laranet is a modular toolkit with framework-like tooling.
- Native ASP.NET Core, EF Core, Razor, Blazor, and Identity remain the platform.
- The admin panel is optional and never a dependency of other modules.
- `Laranet.Admin` must not depend on EF Core. Data access goes through an adapter
  contract.
- No custom view engine, authentication system, ORM, validation engine, or background
  job system.
- Every template and generated file remains ordinary, editable C#.
- Every new package must pass the
  [module admission gates](../architecture/ecosystem.md#9-module-admission-gates).
- Research items are not public API commitments.

## 4. Non-goals

- A Laranet ORM, HTTP server, view engine, authentication system, caching layer,
  mailing system, storage abstraction, or background job runner.
- `Laranet.Security`: use ASP.NET Core Identity and the native authorization model.
- `Laranet.Tasks`: use an existing scheduler or queue when a real requirement appears.
- `Laranet.Cache`, `Laranet.Mail`, `Laranet.Storage`, `Laranet.Logging`,
  `Laranet.Localization`, `Laranet.OpenApi`, and `Laranet.Messaging`: use the platform
  or a focused third-party library.
- Per-provider EF Core packages without provider-specific functionality.
- Repository, Unit of Work, CQRS, mediator, or `Result<T>` generated by default.
- A "measure your SOLID score" tool.

## Sprint 22 — Admin architecture and ADR

**Status: Candidate — blocked by Version 3**
**Priority: High when the milestone starts**

- [ ] Write the admin ADR:
  - Package boundary: `Laranet.Admin` and `Laranet.Admin.AspNetCore`.
  - Resource, field, filter, action, and permission contracts.
  - Data adapter contract for list, search, filter, page, read, create, update, and
    delete.
  - Security model: authentication, authorization, anti-forgery, and audit.
  - Explicit non-goals and provider expectations.
- [ ] Decide how the admin integrates with ASP.NET Core routing and authorization.
- [ ] Confirm that `Laranet.Admin` does not reference EF Core.
- [ ] Review the contract against at least one real application.

**Exit criteria:** the ADR is accepted and the data adapter and security contracts are
documented before implementation.

## Sprint 23 — Admin core (`Laranet.Admin`)

**Status: Candidate — blocked by Sprint 22**
**Priority: High when the milestone starts**

- [ ] Implement provider-neutral resource metadata:
  - `AdminResource<T>` with columns, forms, search, filters, ordering, and
    permissions.
  - Field metadata: label, type, visibility, read-only, formatting, and validation
    hints.
  - Filter and action descriptors.
  - Pagination and search contracts reusable by any data adapter.
- [ ] Keep the core free of Razor, ASP.NET Core, and EF Core.
- [ ] Add unit tests for metadata composition, validation, and permission checks.
- [ ] Document the adapter contract.

Illustrative API — **not committed** until the ADR and prototype validate it:

```csharp
public sealed class ProductResource : AdminResource<Product>
{
    public override void Configure()
    {
        Column(product => product.Name);
        Column(product => product.Price);

        Searchable(product => product.Name);
        Filterable(product => product.CategoryId);
    }
}
```

**Exit criteria:** an adapter can describe a resource without referencing a UI
framework or a database provider.

## Sprint 24 — Admin UI (`Laranet.Admin.AspNetCore`)

**Status: Candidate — blocked by Sprint 23**
**Priority: High when the milestone starts**

- [ ] Render list, detail, create, edit, and delete screens with Razor.
- [ ] Provide layouts, components, and conventional routes.
- [ ] Integrate with ASP.NET Core authentication and authorization.
- [ ] Add anti-forgery protection to every mutating request.
- [ ] Support search, filtering, sorting, and pagination through the core contracts.
- [ ] Support permission checks per resource and per action.
- [ ] Do not create a view engine or a custom authentication system.
- [ ] Add tests covering authentication, authorization, filtering, pagination, and
      CRUD.

**Exit criteria:** the panel is usable with the EF Core adapter, and every mutating
endpoint is protected by authentication, authorization, and anti-forgery.

## Sprint 25 — Admin pilot and data adapters

**Status: Candidate — blocked by Sprint 24**
**Priority: Medium**

- [ ] Implement the EF Core adapter outside the core package.
- [ ] Validate the adapter against SQLite, PostgreSQL, MySQL/MariaDB, and SQL Server.
- [ ] Validate a non-EF path through the adapter contract, without adding a mandatory
      dependency.
- [ ] Pilot the panel in a real application and record the findings.
- [ ] Remove or change any abstraction the pilot proves unnecessary.
- [ ] Document limitations and provider-specific behavior.

**Exit criteria:** the panel works end to end in a real application, and the adapter
contract is proven by at least two implementations or an explicit decision that one is
enough.

## Sprint 26 — Web and Blazor templates

**Status: Candidate**
**Priority: Medium**

- [ ] Add a `blazor` project template using Blazor Web App render modes.
- [ ] Reuse the `mvc` template from Version 3 for Razor Pages and MVC.
- [ ] Keep Razor and Blazor as Microsoft technologies; do not introduce
      `Laranet.Views`.
- [ ] Ensure every template builds without warnings and is tested in CI.
- [ ] Document the render modes and the trade-offs of each template.
- [ ] Do not generate CQRS, mediator, generic repositories, or unit of work by default.

**Exit criteria:** every web template builds in CI and contains only what it promises.

## Sprint 27 — Relationship research and optional adapters

**Status: Research — no public API commitment**
**Priority: Low**

### Eloquent-style relationships

- [ ] Write an ADR that evaluates `HasOne`, `HasMany`, `BelongsTo`, and
      `BelongsToMany` wrappers.
- [ ] Determine how they coexist with native EF Core navigation properties, change
      tracking, metadata, and `Include`.
- [ ] Prototype them behind an experimental API.
- [ ] Do not expose them as a stable public API until a concrete use case and the ADR
      justify it.
- [ ] Keep the Data Mapper approach as the default.

### Dapper adapter

- [ ] Evaluate `Laranet.Data.Dapper` only if a real application needs explicit SQL
      with the Laranet query contracts.
- [ ] Keep the adapter independent; `Laranet.Data` must not reference Dapper.
- [ ] Do not add per-provider packages.

**Exit criteria:** each item ends with an accepted decision: implement, defer, or
reject, with the reasoning recorded.

## Sprint 28 — Ecosystem hardening and next milestone

**Status: Candidate**
**Priority: Medium**

- [ ] Evaluate `Laranet.Analyzers` for verifiable diagnostics:
  - Pagination without deterministic ordering.
  - DTOs that expose EF Core entities.
  - Unsupported package versions.
  - Circular project references.
- [ ] Investigate `Laranet.Testing` only if the admin or generators need shared
      fixtures and helpers.
- [ ] Verify that no optional module leaked into another module's dependencies.
- [ ] Review XML documentation, samples, and guides against the implemented surface.
- [ ] Audit package metadata, icons, and READMEs.
- [ ] Decide whether the next milestone is `1.0.0` or another `0.x` iteration.

**Exit criteria:** the public surface is documented and tested, the dependency graph is
clean, and the next milestone is decided.

## 6. Monthly backlog review

Once a month, review:

1. Issues and GitHub Discussions opened since the previous review.
2. Feedback from real applications using the published packages.
3. Provider test results and any CI failures.
4. Roadmap items whose prerequisites changed.
5. Whether the next sprint still has a concrete use case.

Record the outcome as a short note linked from the
[roadmap index](README.md). Do not create a new document per meeting, and do not
duplicate ADRs in the summary.

## 7. Decision log

| Decision | Outcome |
| --- | --- |
| Admin panel | Candidate for Version 4, gated by ADR, prototype, and security review |
| Admin data access | Adapter contract; core independent of EF Core |
| Admin UI | Razor and ASP.NET Core; no custom view engine |
| Blazor and Razor | Project templates only; no `Laranet.Views` |
| Relationships | Research only; native EF Core navigation remains the default |
| Dapper | Optional adapter, only with a validated use case |
| Testing package | Research only; no broad test framework |
| Analyzers | Candidate, optional, no runtime behavior |
| Security | ASP.NET Core Identity and native authorization |
| Background jobs | Not scheduled; use an existing library when needed |
| Own ORM | Not planned |

## 8. Exit criteria for Version 4

- The admin ADR, data adapter contract, and security model are accepted.
- The admin panel works end to end in a real application.
- The admin core is independent of EF Core and the UI package.
- Web and Blazor templates build in CI.
- Relationship and adapter research ends with explicit decisions.
- The dependency graph is clean and every package is independently consumable.
- The next milestone (`1.0.0` or another `0.x`) is decided and documented.
