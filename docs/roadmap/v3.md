# Version 3 — Application experience

**Status: In progress**
**Priority: Medium**

Version 3 turns the toolkit into a coherent application-building experience without
turning it into a second .NET framework. It builds on the feedback and provider
verification from [Version 2](v2.md).

The theme is **conventions with escape hatches**: Laranet should make the common path
fast and consistent, while keeping native ASP.NET Core, EF Core, and C# available at
any time.

Version 3 does not start until Version 2 has published `0.1.1` and has at least one
round of reviewed feedback.

> **Status note:** `0.1.1` is published. The feedback round is still pending because no
> external feedback has been received. Sprint 14 was started by explicit maintainer
> decision because standards and the generator contract do not depend on that feedback.

## Principles

- [ADR-0006](../architecture/decisions/0006-toolkit-with-framework-tooling.md): Laranet
  is a modular toolkit with framework-like tooling.
- [ADR-0007](../architecture/decisions/0007-simple-generation-profile.md): the
  `simple` generation profile is the default.
- Generated code is ordinary, editable C#, with no mandatory runtime metadata.
- No profile generates `Result`, `Error`, Repository, Unit of Work, CQRS, or mediator
  types unless the user explicitly selects a profile that requires them.
- Every template and profile must build, run, and be tested before it ships.

## Sprint 16 — `make:crud`

**Status: Completed**
**Priority: High**

- [x] Discover the only `DbContext` in the nearest project when `--context` is omitted.
- [x] Preserve overwrite protection, `--dry-run`, `--force`, `--output`, `--flat`,
    and `--interactive`.
- [x] Generate code that builds without warnings.
- [x] Add generation and build tests for every profile.
- [x] Document the files produced by each profile.

**Validation:** the Release build succeeds with zero warnings and the full SQLite

warnings treated as errors. CI runs the same script after the template verification.
Generated application integration tests remain deferred to `make:crud --with-tests`
in Version 5.

**Exit criteria:** `make:crud` is usable end to end, each profile is tested, and the
default output contains no speculative layers.

## Sprint 17 — EF Core conventions

**Status: Completed**
**Priority: Medium**

- [x] Evaluate declarative conventions on top of EF Core:
  - [x] Primary key and entity conventions.
  - [x] Optional `CreatedAt` / `UpdatedAt` auditing.
  - [x] Optional soft delete with a global query filter.
  - [x] Optional global filters.
- [x] Keep the `DbContext` as the center of persistence (Data Mapper).
- [x] Do not introduce `HasMany<T>` / `BelongsTo<T>` wrappers in this sprint.
  Evaluate them later with an ADR and a concrete use case.
- [x] Verify behavior with SQLite, PostgreSQL, MySQL/MariaDB, and SQL Server.
- [x] Document provider-specific differences found by the tests.
- [x] Record an ADR before adding any public convention that expands the API.

**Decision:** entity and primary-key conventions remain native EF Core, and general
global filters remain `HasQueryFilter`. Laranet adds only opt-in `IAuditable` auditing,
`ISoftDeletable` soft delete, `AddLaranetAuditing`, `AddLaranetSoftDelete`, and
`ApplySoftDeleteQueryFilters`. See
[ADR-0009](../architecture/decisions/0009-optional-ef-core-conventions.md) and the
[EF Core conventions guide](../guides/ef-core-conventions.md).

**Validation:** the Release build succeeds with zero warnings and the full SQLite
suite passes 349 tests. The provider compatibility suite passes against SQL Server
2022, PostgreSQL 17, MySQL 8.4, and MariaDB 11.4. The tests document `DateTimeOffset`
behavior: SQLite and SQL Server preserve the offset, PostgreSQL accepts only a UTC
offset, and MySQL/MariaDB normalize to UTC.

**Exit criteria:** conventions are optional, tested against all official providers,
and users can ignore them entirely.

## Sprint 19 — `laranet doctor`

**Status: Planned**
**Priority: Medium**

- [ ] Implement `laranet doctor` with verifiable diagnostics:
  - Circular project references.
  - Unsupported Laranet, .NET, or EF Core versions.
  - Generated files that conflict with existing files.
  - Endpoints that query large tables without pagination (heuristic, configurable).
  - Direct `DbContext` usage in controllers (configurable rule).
  - DTOs that expose EF Core entities (heuristic).
- [ ] Support `--json` output and meaningful exit codes.
- [ ] Do not claim to measure SOLID compliance or architectural quality
  automatically.
- [ ] Add tests for each rule and for the output format.

**Exit criteria:** every diagnostic is deterministic, documented, and covered by
tests.

## Sprint 20 — Admin foundations (candidate)

committed to Version 3 until the conditions in

- [ ] Write an ADR defining the admin boundary, data adapter contract, and security
  model.
- [ ] Prototype list, search, filter, pagination, create, edit, and delete screens.
- [ ] Render with Razor; do not create a view engine.
- [ ] Integrate with ASP.NET Core authentication and authorization.
- [ ] Keep `Laranet.Admin` independent of EF Core.
- [ ] Validate the prototype against a real application.

Full implementation may move to Version 4.

## Decision log

| Decision | Outcome |
| --- | --- |
| Identity | Modular toolkit with framework-like tooling (ADR-0006) |
| Default CRUD profile | `simple` (ADR-0007) |
| Complex profiles | Opt-in only |
| EF Core approach | Data Mapper with declarative conventions first |
| Active Record wrappers | Deferred until an ADR and use case exist |
| Validation | DataAnnotations built in; FluentValidation optional |
| Admin panel | Candidate, gated by ADR, prototype, and security review |
| Own ORM | Research only; not committed |
| Provider packages | No per-provider packages without provider-specific functionality |

## Exit criteria for Version 3

- Standards and generator contract are documented and tested.
- Project templates and `make:crud` profiles build in CI.
- EF Core conventions are optional and verified across official providers.
- Validation and `laranet doctor` are available and documented.
- The admin decision is recorded, even if implementation moves to Version 4.
