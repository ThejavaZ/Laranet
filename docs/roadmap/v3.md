# Version 3 — Application experience

**Status: Planning**
**Priority: Medium**

Version 3 turns the toolkit into a coherent application-building experience without
turning it into a second .NET framework. It builds on the feedback and provider
verification from [Version 2](v2.md).

The theme is **conventions with escape hatches**: Laranet should make the common path
fast and consistent, while keeping native ASP.NET Core, EF Core, and C# available at
any time.

Version 3 does not start until Version 2 has published `0.1.1` and has at least one
round of reviewed feedback.

## Principles

- [ADR-0006](../architecture/decisions/0006-toolkit-with-framework-tooling.md): Laranet
  is a modular toolkit with framework-like tooling.
- [ADR-0007](../architecture/decisions/0007-simple-generation-profile.md): the
  `simple` generation profile is the default.
- Generated code is ordinary, editable C#, with no mandatory runtime metadata.
- No profile generates `Result`, `Error`, Repository, Unit of Work, CQRS, or mediator
  types unless the user explicitly selects a profile that requires them.
- Every template and profile must build, run, and be tested before it ships.

## Sprint 14 — Development Standards and generator contract

**Status: Planned**
**Priority: High**

- [ ] Write `docs/development/standards.md`: naming, project structure, async and
  cancellation, validation, error handling, DTOs, dependency direction, testing, and
  when an interface or repository is justified.
- [ ] Define the generator contract independently from the CLI commands:
  `IGenerator`, `GenerationContext`, `GeneratedFile`, and dry-run/force/output
  handling.
- [ ] Document how templates are discovered and overridden.
- [ ] Add tests for generation planning and conflict detection.
- [ ] Review the contract against the existing CLI generators.

**Exit criteria:** the standards document is the reference for every generator, and
generators can be invoked independently of the command-line layer.

## Sprint 15 — Project templates

**Status: Planned**
**Priority: High**

- [ ] Add project templates:
  - `minimal-api` (default for APIs)
  - `mvc` with Razor views
  - `layered` with presentation, application, domain, and infrastructure
  - `hexagonal` with ports and adapters
  - `modular` with feature folders
- [ ] Ensure each template builds without warnings.
- [ ] Add a CI test that creates and builds every template.
- [ ] Document the files and trade-offs of each template.
- [ ] Do not add CQRS, mediator, generic repositories, or unit of work by default.

**Exit criteria:** every template builds in CI and produces a project that only
contains what the template promises.

## Sprint 16 — `make:crud`

**Status: Planned**
**Priority: High**

- [ ] Implement `laranet make:crud <Entity>` with the profiles from ADR-0007:
  - `simple` (default): endpoint or controller, request/response DTOs, direct
    `DbContext` usage, validation, and tests.
  - `standard`: adds a service class and mapping when the operation is more than a
    thin CRUD. Interfaces only at real boundaries.
  - `clean`: explicit layers, interfaces, repository, and use-case boundaries.
  - `modular`: feature folders with `standard`-level abstraction.
- [ ] Preserve overwrite protection, `--dry-run`, `--force`, and `--output`.
- [ ] Generate code that builds without warnings.
- [ ] Add generation and build tests for every profile.
- [ ] Document the files produced by each profile.

**Exit criteria:** `make:crud` is usable end to end, each profile is tested, and the
default output contains no speculative layers.

## Sprint 17 — EF Core conventions

**Status: Planned**
**Priority: Medium**

- [ ] Evaluate declarative conventions on top of EF Core:
  - Primary key and entity conventions.
  - Optional `CreatedAt` / `UpdatedAt` auditing.
  - Optional soft delete with a global query filter.
  - Optional global filters.
- [ ] Keep the `DbContext` as the center of persistence (Data Mapper).
- [ ] Do not introduce `HasMany<T>` / `BelongsTo<T>` wrappers in this sprint.
  Evaluate them later with an ADR and a concrete use case.
- [ ] Verify behavior with SQLite, PostgreSQL, MySQL/MariaDB, and SQL Server.
- [ ] Document provider-specific differences found by the tests.
- [ ] Record an ADR before adding any public convention that expands the API.

**Exit criteria:** conventions are optional, tested against all official providers,
and users can ignore them entirely.

## Sprint 18 — Validation

**Status: Planned**
**Priority: Medium**

- [ ] Keep DataAnnotations as the built-in validation mechanism.
- [ ] Evaluate an optional FluentValidation integration.
- [ ] Decide the package boundary: `Laranet.AspNetCore.Validation` or a broader
  `Laranet.Validation`.
- [ ] Integrate through native ASP.NET Core endpoint filters or MVC filters.
- [ ] Do not create a custom validation engine or a `FormRequest` clone.
- [ ] Add tests for valid and invalid requests, including the error response shape.
- [ ] Document how to opt out and use native ASP.NET Core validation.

**Exit criteria:** validation is optional, uses native ASP.NET Core behavior, and does
not add a mandatory dependency to unrelated packages.

## Sprint 19 — `laranet doctor`

**Status: Planned**
**Priority: Medium**

- [ ] Implement `laranet doctor` with verifiable diagnostics:
  - Circular project references.
  - Unsupported Laranet, .NET, or EF Core versions.
  - Generated files that conflict with existing files.
  - Endpoints that query large tables without pagination (heuristic, configurable).
  - Direct `DbContext` usage in controllers (configurable rule).
  - DTOs that expose EF Core entities (heuristic).
- [ ] Support `--json` output and meaningful exit codes.
- [ ] Do not claim to measure SOLID compliance or architectural quality
  automatically.
- [ ] Add tests for each rule and for the output format.

**Exit criteria:** every diagnostic is deterministic, documented, and covered by
tests.

## Sprint 20 — Admin foundations (candidate)

**Status: Candidate — requires an ADR and a validated use case**
**Priority: Low**

A Django-inspired administrative panel is a valuable differentiator, but it is not
committed to Version 3 until the conditions in
[the ecosystem architecture](../architecture/ecosystem.md#8-admin-module-django-inspired)
are met.

- [ ] Write an ADR defining the admin boundary, data adapter contract, and security
  model.
- [ ] Prototype list, search, filter, pagination, create, edit, and delete screens.
- [ ] Render with Razor; do not create a view engine.
- [ ] Integrate with ASP.NET Core authentication and authorization.
- [ ] Keep `Laranet.Admin` independent of EF Core.
- [ ] Validate the prototype against a real application.

Full implementation may move to Version 4.

## Decision log

| Decision | Outcome |
| --- | --- |
| Identity | Modular toolkit with framework-like tooling (ADR-0006) |
| Default CRUD profile | `simple` (ADR-0007) |
| Complex profiles | Opt-in only |
| EF Core approach | Data Mapper with declarative conventions first |
| Active Record wrappers | Deferred until an ADR and use case exist |
| Validation | DataAnnotations built in; FluentValidation optional |
| Admin panel | Candidate, gated by ADR, prototype, and security review |
| Own ORM | Research only; not committed |
| Provider packages | No per-provider packages without provider-specific functionality |

## Exit criteria for Version 3

- Standards and generator contract are documented and tested.
- Project templates and `make:crud` profiles build in CI.
- EF Core conventions are optional and verified across official providers.
- Validation and `laranet doctor` are available and documented.
- The admin decision is recorded, even if implementation moves to Version 4.
